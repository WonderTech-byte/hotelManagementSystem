HOTEL MANAGEMENT SYSTEM API DOCUMENTATION
=========================================

Project: HotelManagementSystem
Document type: Plain-text API reference
Generated from: source controllers/DTOs under src/main/java and compiled feature endpoints under target/classes


1. OVERVIEW
-----------
Base path groups:
- /api/auth
- /api/rooms
- /api/bookings
- /api/users
- /api/features   (present in compiled classes; source controller is missing from src)

Authentication:
- JWT bearer authentication is used for protected endpoints.
- Public endpoints:
  - /api/auth/**
  - GET /api/rooms/**
- Role-restricted endpoints:
  - GUEST:
    - POST /api/bookings
    - GET /api/bookings/my
    - PATCH /api/bookings/{id}/cancel
  - FRONT_DESK or ADMIN:
    - PATCH /api/bookings/{bookingCode}/checkin
    - PATCH /api/bookings/{bookingCode}/checkout
    - GET /api/bookings
    - GET /api/bookings/{bookingCode}
  - ADMIN:
    - POST /api/rooms/**
    - PUT /api/rooms/**
    - DELETE /api/rooms/**
    - /api/users/**
- Security config in source does not explicitly mention /api/features/**. That means these endpoints fall through to authenticated access unless additional rules exist elsewhere.

Common response content:
- Most endpoints return JSON.
- Multipart endpoints accept form-data and may still return JSON.

3. SHARED ERROR RESPONSE
------------------------
Validation and runtime errors are returned as JSON with this shape:

{
  "timestamp": "2026-04-07T12:34:56",
  "status": 400,
  "error": "Bad Request",
  "message": "Validation failed",
  "path": "/api/auth/register",
  "details": [
    "email: must be a well-formed email address",
    "password: size must be between 6 and 2147483647"
  ]
}

Fields:
- timestamp: LocalDateTime
- status: HTTP status code
- error: HTTP reason phrase
- message: summary message
- path: request URI
- details: list of validation/detail messages

Typical failure status observed in code:
- 400 Bad Request


4. AUTH API

4.1 POST /api/auth/register
Auth:
- Public
Content-Type:
- application/json
Request DTO:
- RegisterRequestDTO

Schema:
{
  "fullName": "string",        // required, not blank
  "username": "string",        // required, not blank, must be unique
  "email": "user@example.com", // required, not blank, valid email, must be unique
  "password": "string",        // required, not blank, minimum length 6
  "phoneNumber": "string",     // optional
  "userType": "GUEST"          // required by DTO; service defaults to GUEST only if null slips through
}

Success response:
- 200 OK
- AuthResponseDTO

Response shape:
{
  "token": "jwt-token",
  "user": {
    "id": 1,
    "fullName": "string",
    "username": "string",
    "email": "string",
    "phoneNumber": "string",
    "userType": "ADMIN | FRONT_DESK | GUEST",
    "active": true,
    "createdAt": "2026-04-07T12:34:56"
  }
}

Notes:
- Duplicate username returns 400 with message "Username already taken".
- Duplicate email returns 400 with message "Email already registered".

5.4 POST /api/rooms
Auth:
- ADMIN
Content-Type:
- multipart/form-data
Request DTO:
- CreateRoomDTO

Form-data schema:
- roomNumber: string, required, not blank
- roomType: enum RoomType, required
- price: number, required, positive
- priceType: enum PriceType, required
- description: string, optional
- imageFiles: file[], optional
- features: string, optional

Important note about features:
- `features` is not a nested JSON body field in an application/json request.
- It is a multipart text field containing a JSON array string.
- Each item in that JSON array follows AddRoomFeatureDTO shape:
  {
    "roomFeature": "string",   // required, not blank
    "description": "string"    // optional
  }
- `imageFile` exists on AddRoomFeatureDTO but is not parsed from the `features` JSON string during room creation.

Example multipart text value for `features`:
[
  {
    "roomFeature": "Ocean View",
    "description": "Faces the beach"
  },
  {
    "roomFeature": "Mini Bar",
    "description": "Stocked on request"
  }
]

Success response:
- 201 Created
- RoomDTO

Notes:
- Duplicate room number returns 400.
- Invalid `features` JSON returns 400 with message similar to:
  - "Invalid features JSON. Expected a JSON array of feature objects."
- Duplicate feature name inside a room returns 400.

6. BOOKING API
--------------

6.1 POST /api/bookings
Auth:
- GUEST
Content-Type:
- application/json
Request DTO:
- BookingRequestDTO

Schema:
{
  "roomId": 1,                 // required
  "checkInDate": "2026-05-01",   // required, must be a future date
  "checkOutDate": "2026-05-05",  // required
  "numberOfUnits": 1           // minimum 1, defaults to 1 if omitted by Java object initialization
}

Additional business rules from service:
- checkOutDate must be after checkInDate
- checkInDate cannot be in the past
- room must exist
- room status must be AVAILABLE
- room must not already be booked for selected dates

Success response:
- 201 Created
- BookingResponseDTO

BookingResponseDTO shape:
{
  "id": 1,
  "bookingCode": "BK-ABC123",
  "guest": {
    "id": 1,
    "fullName": "string",
    "username": "string",
    "email": "string",
    "phoneNumber": "string",
    "userType": "ADMIN | FRONT_DESK | GUEST"
  },
  "room": { RoomDTO },
  "checkInDate": "2026-05-01",
  "checkOutDate": "2026-05-05",
  "numberOfUnits": 1,
  "numberOfNights": 4,
  "totalPrice": 600.0,
  "status": "CONFIRMED | CHECKED_IN | CHECKED_OUT | CANCELLED | NO_SHOW"

10. IMPLEMENTATION NOTES
------------------------
- Room creation accepts multipart form-data, not a JSON document.
- Nested room features during room creation are sent as a JSON string inside the `features` form field.
- Validation errors and many business-rule failures are normalized to HTTP 400.
- Some API surface exists only in compiled artifacts (`target/classes`) and not in source, so this document flags those endpoints explicitly.
